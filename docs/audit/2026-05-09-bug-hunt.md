# 全面 Bug 排查 — 2026-05-09

**触发场景**：14 天 × 3 seed × 4 variant publishable suite 跑出 traj_dev hp = gd 到 12 位小数、phone_friction 与 baseline 全字段 byte-identical 的"纯空"结果。先怀疑是注意力位移 thesis 不成立；排查后发现是**测量/装配链路有多处 bug 把信号洗掉了**。

测试基线：`pytest tests/ -v` → **1123 passed, 3 skipped**。单元层无回归；问题全在 suite-wiring 与 metric 装配上。

---

## 严重度分级

- **B1–B4 = blocker**：让 thesis 信号无法被观察到的测量 bug，必须修。
- **B5–B6 = major**：metric 计算错对象 / metadata 污染。
- **B7–B8 = minor**：可观测性 / 复现锁条目错误。

---

## B1 (blocker) `traj_dev_m` 把 10 个 protag 的信号稀释进 90 个 scripted agent 的噪音里

`metrics/factory.py::_compute_trajectory_deviation_m` (52–108) 取 `per_day[interv_end].end_of_day_location_by_agent` 然后对**全部 100 个 agent** 跑 median：

```python
for _agent_id, loc_id in end_locations.items():    # 100 agents
    distances.append(math.sqrt(dx*dx + dy*dy))
return float(statistics.median(distances))         # 50th-percentile = 第 50 个 agent
```

但只有 protag(10) 接到 hp 的 `target_location` 推送、且会被 ai-town do_something 路径影响行动；剩下 90 个 scripted agent 在 hp / gd / baseline 三种 variant 下 end-of-day 位置**完全相同**（per-agent diff 抽样：90/100 → 93/100 在 hp vs gd 同 seed 下逐字节一致）。

后果：median = 第 50 个 agent，几乎一定是 scripted agent → **hp seed42 = gd seed42 = 206.876921…(12 位小数全等)**。这不是 thesis 失败，是测量对象错了。

**修法**：metric 改成只对"接到 push 的 agent 集合"取 median——即 `target_agent_ids ∩ end_locations.keys()` 的子集。或者出两个版本（all-agent + protag-only）以方便对比 spillover。

## B2 (blocker) `global_distraction` variant 在 stub-replan 路径下是 **operationally inert**

`tools/suite_stub_llm.py::StubReplanLLM` 的 dispatch 表（line 100–113）：

```
hyperlocal_push    → _plan_toward(target_location)   # 真的改 plan
global_distraction → "<plan></plan>"                  # 空 plan
phone_friction     → "<plan></plan>"                  # 空 plan
shared_anchor      → _plan_toward(community)
```

`agent/planner.py::Planner.replan` 收到空 plan 时（line 528–535）：

```python
new_future_steps = _parse_xml_plan(raw)
if not new_future_steps:
    return current_plan.model_copy(deep=True)   # 还旧 plan
```

→ gd 触发了 44/57/105 次 replan、`replan_count` 都正常增长，但**返回的全是旧 scripted_plan 的深拷贝**，agent 实际行为与 baseline **逐 tick 完全相同**。

证据：
- gd `encounter_stats` 三个 seed 全部 byte-identical 于 baseline（18983.0 / 35117.0 / 27372.0）
- gd `weak_tie_formation_count` 也全等于 baseline（3372 / 4376 / 3996）

修复方向（任选其一）：
1. StubReplanLLM 也给 gd 一个真的会改 plan 的 stub（比如随机扔出去做无关事的 step），让"global news 干扰"在 stub 路径里有可测的效应。
2. 把 stub 路径下的 gd 直接标 `expected = no-effect`，metric 报告里说明它在 stub 模式下不参与对比；想要真效应必须 `--use-real-llm` 走 LLM 路径。
3. 把 contest.json 的 `mirror_delta` 计算改成"识别 inert variant → emit warning"。

## B3 (blocker) `phone_friction` variant 在当前 pipeline 下也是 **operationally inert**

`policy_hack/variants/phone_friction.py::apply_intervention_start` 修改 `runtime.profile.digital`：
- `daily_screen_hours *= 0.5`
- `notification_responsiveness *= 0.5`
- `feed_bias = "local"`

但这三个字段在 sim 链路里**只被两处消费**：

1. `agent/runtime.py:973-979 build_observer_context` —— 写进 `AttentionState`，给 `PerceptionPipeline` 渲染主观视图用。
2. `attention/service.py` —— `feed_bias_suppression` 决定 feed item 是否被丢弃（baseline 没有 feed item 注入，所以这个分支也不触发）。

而 movement / encounter / 路径选择由 `scripted_plan`（deterministic）决定；ai-town do_something LLM 上下文里也不读 digital。所以 friction 修了一个**没有下游 reader** 的字段。

证据：phone_friction 与 baseline 在 **encounter_stats 全部字段 + weak_tie + replan_count(都=0) + dialogue_count + reflection_count** 上**逐字节相等**。

修复方向：
1. 让 phone_friction 在 intervention 期向所有 agent 注入"physical_world 注意力 boost" 类型的 trigger event → 走 memory → replan 路径，强行制造 plan-level 行为变化。最贴近 H_pull 的语义。
2. 或者改成"intervention 期把每个 agent 当前 plan 里 1–2 个 phone-related step 删掉、替换为 outdoor step"——直接在 plan 层动手术。
3. 至少要让 friction 触发的 replan_count > 0，否则它和 baseline 的 phase 一样是空跑。

## B4 (blocker) `phone_friction` 的 primary metric 选择不可区分自身

`contest.json` 给 phone_friction 选的 primary metric 是 `attention.phone_feed_proxy`，baseline = pf = `0.0` → CI = [0, 0] → 永远 inconclusive。

`phone_feed_proxy` 由 `attention.allocation_ratio.phone_feed_proxy` 来——它是 `delivered_feed_items / something`，因为 baseline 和 pf 都不注入 feed item，所以两边都是 0。

修法：phone_friction 的 primary metric 应换成"physical_world allocation 占比"或"户外步数 / encounter 密度"——任何 friction 应该提升的指标。当前选择是个 **degenerate metric**，写出来就是 0。

## B5 (major) `traj_dev_m` 对 `global_distraction` 测错了对象

`metrics/factory.py:68` 允许 hp 和 gd 都计算 `traj_dev_m`，但 gd 的语义是"全球 broadcast，没有 location"。`tools/run_variant_suite.py:739-741` 强行把 hp 的 `target_location` 注入到 gd 的 `variant_metadata`：

```python
if variant_name in {"hyperlocal_push", "global_distraction"} and target_location:
    variant_metadata["target_location"] = target_location
```

→ gd 的 traj_dev_m 是"100 个 agent 到一个 hp 才用得上的 location 的中位距离"，与 gd 的实验语义无关。在 contest.json 里它被当作 primary metric 与 hp 对比，得出 `mirror_delta = 0.0`。

修法：
- 要么 gd 的 primary metric 换成"轨迹熵下降 / 户外停留时间下降"
- 要么明确：gd 与 hp 共用 traj_dev 但 measurement = "agents drifting AWAY from hp's target"，direction 取反

当前的"复用 hp target"语义不清晰。

## B6 (major) `cost_breakdown` 在 Gemini provider 下永远是 0

`tier_llm_factory.py::_GeminiTierClient.generate` 没记 token / cost。`metrics` 收集时全部默认为 0。后果：
- `cost_breakdown.total = 0` 看起来像没花钱，实际花了几小时 Gemini quota
- `reproducibility_lock.model_version = "stub:v1"` 即便 ai-town 用了 Gemini 仍然显示 stub（因为 rep_lock 看的是 `--use-real-llm` flag，flag 是 planner-only 的，不知道 ai-town stack 用的是哪家）

修法：rep_lock 增加 `aitown_provider` 字段（`gemini` / `anthropic` / `stub`），让 model_version 至少能反映"哪家家谱在跑"。cost_breakdown 短期可以接受 0，长期要改 Gemini client 记 input/output tokens。

## B7 (minor) `replan_count` 包含"空 replan"（plan 没改但计数 +1）

`memory/service.py:441-442`：

```python
new_plan = asyncio.run(planner.replan(...))   # 可能返回 deep_copy(unchanged)
agent.plan = new_plan
replans.append((agent_id, candidate))
self._replan_count_today[agent_id] = replan_count + 1
```

无论 LLM 返回的是真新 plan 还是 fallback 旧 plan 的深拷贝，`replan_count_today` 都 +1。后果：suite output 里 gd 的 `replan_count = 44/57/105` 让人误以为 gd 真改了 plan，其实里面 100% 是空 replan。

修法：检查 `new_future_steps` 是否真的非空再 +1。或者拆两个 counter：`replan_attempted` vs `replan_changed_plan`。

## B8 (minor) `reproducibility_lock.phase_config` 字段被字符串索引污染

`tools/run_variant_suite.py:766-769`：

```python
phase_config={
    "baseline_days": phase_days[0],   # phase_days 是 str "4,6,4"
    "intervention_days": phase_days[1],  # "," 字符
    "post_days": phase_days[2],        # "6"
},
```

phase_days 在这一行还是参数原始字符串，没有 split 成 list。结果存进 rep_lock 的是：
```
"baseline_days": "4",
"intervention_days": ",",
"post_days": "6",
```

只影响 reproducibility metadata（实际 phase scheduling 是 `controller.model_dump()` 在更上面，那条是对的）。

修法：直接 `parts = [int(x) for x in phase_days.split(",")]` 然后传 `parts[0]/[1]/[2]`。

## 影响汇总（thesis 视角）

回到 user 提的本质："打碎个体对附近的隔阂感"。当前 suite 跑出来的"null 结果"几乎全部由 B1+B2+B3 制造：

| Variant | 看似的 null 来源 | 真正发生的事 |
|---|---|---|
| baseline | （reference） | 正常空跑 |
| hyperlocal_push | encounter -6.8% / weak_tie -2.8% | **真信号**：10 protag 真被拉到 target_location，触发了不同的 encounter 模式。**只是被 90 个 scripted agent 的固定路径稀释成"看起来很小"。** |
| global_distraction | encounter = baseline byte-identical | **B2 操作性失效**：StubReplanLLM 给 gd 永远返回空 plan，agent 行为不变 |
| phone_friction | 全字段 = baseline byte-identical | **B3 操作性失效**：digital_profile 没有下游 reader |

**hp 的 -6.8% encounter delta 是真信号**，但被 measurement (B1) 和报告框架（用 traj_dev 而不是 protag-only 指标）一起遮掉了。把 metric 算到 protag-only 子集，预计 effect size 会放大约 10×。
